# 工作流架构

## 职责

| 模块 | 负责内容 |
| --- | --- |
| `config.py` | 配置、路径和后端选择。 |
| `games/` | 游戏资源获取、原文提取、上下文和客户端映射。 |
| `prepare.py`、`session.py` | 增量计划、术语、答案保存和完成校验。 |
| `merge.py`、`build.py` | 发布预检、文件更新和 manifest。 |
| `codex.py`、`translate.py` | 执行设置、进程控制和输入保护。 |
| `run.py`、`agent.py`、`ci.py` | 用户操作、会话工具和 CI 入口。 |

游戏适配器提供[规范化条目](adapters.md)，核心不依赖具体游戏表名或客户端键规则。Codex 读取上下文、提交译文并根据校验结果修订；合并由独立步骤完成。Node 静态服务只读取交付文件。

## 一次更新

根据已有译文和检查范围获取原文 → 提取共享清单 → 按语言比对原文与译文 → 确定术语 → 翻译其余文本 → 校验全部结果 → 合并。

原文获取和提取由各语言共享，译文、术语和状态按语言隔离。category 表示文本用途，group 表示上下文组；`term=true` 决定术语先行。提交批次由 Agent 根据上下文选择。

## 增量与状态

| 数据 | 用途 |
| --- | --- |
| 条目 ID | 标识游戏中的文本；同文异境可用不同 ID。 |
| 任务 ID | 标识特定目标语言、原文和翻译依据下的一次任务。 |
| 计划与结果 | 保存本次任务、发布位置、旧值和已校验译文。 |
| 持久状态 | 记录固定 ID 的原文版本、术语绑定和审阅清单，与译文一起提交；以原文为键的本游戏不需要记录已译资源版本。 |
| 工作缓存 | 保存答案和进度；runtime 绑定当前机器路径，可重新生成。 |

原文、相关上下文、规则、风格或有效术语变化会影响答案复用。模型后端和机器路径不参与语义身份，发布位置变化只影响合并条件。

固定 ID 的原文修订产生新任务；已发布内容不会仅因换模型而重翻。本游戏日常根据剧情译文文件是否存在决定下载范围，names 来自所选剧情，masterdata 始终按原文键比较。`--check-existing` 才重新获取全部剧情，检查已有字典中的漏译、原文变化及旧输出。规范变化生成保守的文件审阅清单。术语的引用和分类规则见[术语表文档](../glossary/README.md)。

## 发布保证

全部所选语言先完成预检，再逐文件原子替换，manifest 最后写入。每个位置必须仍为规划时的旧值或本次目标值，完整应用后的术语指纹也必须一致，因此中断后可以重跑 merge。多文件更新以 Git 提交作为完整交付版本。

原文快照在会话开始和完成时校验；Agent 对受保护输入的修改会使流程失败。结构和格式由代码校验，语义与风格由 Agent 或人工审阅。

CI 的原文缓存用于避免重复下载，不代表翻译完成状态；跨任务只传当前检查范围的清单及引用原文包。答案保存在恢复缓存中；发布阶段只接收计划、结果和报告，并重建本机路径。任何目标失败都停止本次发布。
